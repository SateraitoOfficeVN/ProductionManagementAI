# documentation rules

- Write new system artifacts in English unless another language is requested. English is the source of truth.
- Markdown documents under `docs/en/` are English only; do not write Japanese `.md` files. Each document is also published as two PDFs (RFC 0008):
  - `docs/en/pdf/<path>.pdf`, rendered from the English Markdown, and `docs/ja/pdf/<path>.pdf`, rendered from a Japanese translation of it. `<path>` is the document's path under `docs/en/` (for example `010_basic-design/001/001_BD_製造指示登録・編集`).
  - Render both with `python scripts/docs-pdf.py`. For the Japanese PDF, translate the English Markdown into a temporary file outside the repository, keep its relative links and image paths unchanged, and pass `--lang ja --base <the English document's folder>`. The translation is not committed.
  - Regenerate both PDFs in the same change as any edit to the English document. Put the document ID and revision (Document control version, otherwise last-updated date) in `--source-note`, so each PDF names the revision it was rendered from.
  - In the Japanese translation, keep the English structure (sections, numbering, tables, diagrams) and translate prose, headings, table headers, descriptions and Mermaid labels. Keep as they are: IDs, code, identifiers, routes, file paths, API and column names, and enum values. Quoted UI text and messages appear in Japanese alone, without the English gloss.
  - An existing document without PDFs gets them the first time it is edited, however small the edit.
  - Not covered: `README.md` index files, work-item records, HTML mockups, and files that are already PDFs.
  - An HTML mockup is not rendered to PDF. It has a Japanese edition beside it, `<name>.ja.html` in the same `mockups/` folder, with the page captions in Japanese as well as the UI; the Japanese PDF of the DD links to that edition's Artifact, the English PDF to the English one. Update both editions in the same change (WI-005).
- Quote UI text and messages exactly as the UI shows them. The UI is Japanese (WI-005 DEC-001), so an English document quotes the Japanese text followed by an English gloss in parentheses, for example 「製品を選択してください。」 (Select a product.), and a catalog or value-mapping table gives the Japanese text and the gloss in their own columns. The Japanese text must match the frontend catalog (`src/frontend/src/features/production-orders/messages.ts`) character for character. Wireframes and mockups show the Japanese text alone.
- Document IDs and file names put the number first (RFC 0010): `###_BD`, `###_DD` with its companions `###_DD-API`, `###_DD-FN` and `###_DD-SPD`, `###_DB`, and `NNNN_ADR` (four digits, MADR). A screen's BD, DD and DB designs share one number (`001_BD`, `001_DD`, `001_DB` are all Screen A); a DB design that serves no screen, such as a foundation schema, takes `000_DB`, and a screen with no database change has no DB design, leaving its number unused. A document's file is `<ID>_<slug>.md` (for example `001_BD_製造指示登録・編集.md`). For a document that shares a screen's number (BD, DD and its companions, DB), the slug is the screen's Japanese name as the UI heading shows it, the same for every document with that number (RFC 0011): `製造指示登録・編集` (SCR-001, whose create and edit headings differ, so the reviewer chose the name, recorded in RFC 0011), `製造指示一覧` (SCR-002), `ダッシュボード` (SCR-003). A document that serves no screen (`000_DB`, the ADRs) keeps an English kebab-case slug (`000_DB_identity-schema.md`); its wireframes, mockups and PDFs start with the same ID (`001_BD_SCR-001-pc.svg`). Each document sits in a folder named by its number inside its type folder, together with everything that shares the number: `010_basic-design/001/` holds `001_BD_….md` and `wireframes/`; `020_detailed-design/001/` holds the main DD, its three companions, `wireframes/` and `mockups/`; `database/001/` and `architecture/0001/` hold one document each. The PDFs mirror these folders under `docs/en/pdf/` and `docs/ja/pdf/`. Other IDs (`REQ-###`, `SCR-###`, `DEC-###`, `TC-###` and so on) keep their form.
- Preserve stable IDs across languages; translations identify their source revision.
- Separate confirmed facts, proposals, assumptions and open questions.
- Link requirements to BD/DD, database/API decisions and test evidence.
- Update documentation in the same change as the code/config it describes; do not defer it to a follow-up.
