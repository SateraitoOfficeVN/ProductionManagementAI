## Field definitions and validation

### Type values (shared by backend and frontend)

| Code (API, DB) | C# enum | Label | Order |
| --- | --- | --- | --- |
| `FINISHED` | `Finished` | 完成品 | 1 |
| `SEMI_FINISHED` | `SemiFinished` | 半製品 | 2 |
| `PART` | `Part` | 部品 | 3 |
| `RAW_MATERIAL` | `RawMaterial` | 原材料 | 4 |

Frontend: `export const productTypes = ['FINISHED', 'SEMI_FINISHED', 'PART', 'RAW_MATERIAL'] as const` in `api.ts`;
labels in `messages.ts` `products.types` record keyed by code. Options render in this order.

### Screen items

| No. | Item | Element / id | Rule |
| --- | --- | --- | --- |
| 8 | Filter 「種別」 | `<select id="type-filter" name="type">`, label 「種別」 | Options: value `""` 「すべて」, then the four codes. Initial value from URL `type` if it is one of the codes, else `""`. Placed after 「状態」 in the filter grid (grid tracks keep the zero minimum from WI-014) |
| 9 | Column 「種別」 | `<td>` after 製品名; SP card `<span>種別：{label}</span>` before 単位 | Label from `products.types[item.type]` |
| 10 | Form 「種別」 | `<select id="type" name="type" required>`, label 「種別」 + required marker | Create: initial `""` shown as 「選択してください」. Edit: loaded `item.type`. Never read-only |

### Client validation (on Save, before the request, like the other fields)

| Condition | Field message | Focus order |
| --- | --- | --- |
| `draft.type` not one of `productTypes` | MSG-E026 「種別を選択してください。」 | After 製品名, before 単位 (follows the visual order) |

Server `VALIDATION` on `type` (400) maps to the same message, as the page already maps server field errors.

### Messages (`products` words)

| Key | Text | ID |
| --- | --- | --- |
| `type` | 種別 | — |
| `typePlaceholder` | 選択してください | — |
| `types` | `{ FINISHED: '完成品', SEMI_FINISHED: '半製品', PART: '部品', RAW_MATERIAL: '原材料' }` | — |
| `typeRequired` | 種別を選択してください。 | MSG-E026 (next free error ID after MSG-E025) |

## Loading, empty, error and success states

No new state. A type filter with no matches shows the existing 「条件に一致する製品はありません。」. The saved-but-hidden
notice (WI-013) also fires when a saved product's type no longer matches the applied type filter.

## URL state

| Param | Parse | Write |
| --- | --- | --- |
| `type` | Kept only if it is one of `productTypes`; otherwise removed with `replace` navigation, like an invalid `state` | Set on 検索 when not `""`; removed on クリア or when 「すべて」 is searched. Preserved by paging, 表示件数 and the return URL passed to create/edit |

The list request sends `type` only when set.

## Accessibility, security and observability

- Both selects have `<label for>`; the required marker is the existing text marker; errors use `aria-invalid` and
  `aria-describedby="type-error"`, and appear in the error summary (WCAG 2.2 AA, same as other fields).
- The type is not sensitive; no telemetry change. Server re-validates every value (004_DD-API-TYPE).

## Test viewpoints

| Level | Viewpoint |
| --- | --- |
| Backend unit | Validation: missing/unknown/each valid `type` on create and update; list query accepts each code, rejects others |
| Integration | Create/update round-trip; filter returns only that type and combines with `q`/`state`/paging; 400 on bad `type`; migration on a populated DB gives the 004_DB-TYPE mapping and `FINISHED` for other rows; `pmai_app` can update `product_type` |
| Frontend unit | Filter URL parse/write (valid, invalid, クリア); column and card label; create without type → MSG-E026 and focus; edit preloads type; type editable when unit locked; dirty guard on type change |
| E2E | Create with type → list shows it; filter by 部品 → only parts, URL `type=PART`, kept across paging and return-after-save; edit type; axe on list and form; SP card shows type |
| Regression | Existing E2E/fixtures that create products send a type |
