## Design rationale

- **DEC-005:** A model-managed EF seed may generate later `UpdateData`/`DeleteData` for the same 30 rows, which would overwrite catalog edits or remove referenced products. Earlier migrations still insert those rows in a fresh database. The current model removes `HasData`, and the new migration removes scaffolded data-delete operations. The additive migration fills the seven-value `unit` field per part using the reviewed mapping in [004_DB](../../docs/en/database/004/004_DB_製品マスタ.md), while preserving IDs, SKU, names and order FKs. A non-seed row with no unit blocks the NOT NULL migration until its unit is selected; it is not silently assigned an inaccurate value. This is an implementation strategy under the approved design scope, not a change to the user's business rule.
- **DEC-006:** A simple active check can race a concurrent retirement. The order write holds a row share lock on its target product through commit, while retirement updates the same row. PostgreSQL serializes these operations, so a new selection cannot commit after an already committed retirement. This changes the order service transaction sequence but not its external success behavior.
